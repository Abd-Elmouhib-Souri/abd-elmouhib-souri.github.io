How I work

The habits behind the numbers above. I apply them to my own projects first.

Audit before training

In DataScoop I rebuilt the exact Keras validation split, found 195 groups of exact duplicates and near-identical augmented copies across it, and kept only the 3,153 validation images with no copy in training. Auditing my own first MindCare showed that its 88% recall came from 50 sentences copied 3,000 times.

Fix the decision rule before the experiment

For MedRAG's reranker I wrote down what "better" meant (accuracy gain and a latency limit) before running bge-reranker-v2-m3, so I could not pick the rule after seeing the result. MedBox's protocol is committed before each run, and its code is committed after its design.

Keep a test set I touch once

MedRAG was tuned on 32 development questions and reported on 19 held-out ones. When the held-out run exposed a drug-class error, I reported it instead of fixing it on the test set. MedBox v2's independent test is still pending, so I report its development numbers as development numbers.

Refuse rather than guess

MedRAG's gate refuses when no passage is relevant, and the LLM is never called. In MedBox, a lower threshold would have turned an OCR reading of a molecule into another laboratory's product, so the system refuses instead.

Publish the negative result

MedBox v1 never gave a wrong drug name but never recognized one either, and I published that with the error analysis. ForgeAI's pre-registered test failed (every idea scored 7.0), so I published it and traced the cause.

Tests that fail when the bug returns

Each security or safety fix gets a test, and I check that the test fails when I put the old code back. DataScoop has 28 backend and 17 Python tests, MedRAG has 38 and MedBox 16.
